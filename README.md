## How I test

Because "attention to detail" on a CV means nothing. This is what I actually do:

- **Risk first, coverage second.** I ask what hurts the business if it breaks, not what's quickest to check. A broken checkout outranks a misaligned label on a page nobody opens.
- **Severity and priority are different numbers.** A crash in a feature used twice a year is high severity, low priority. Confusing the two is how teams end up fixing the wrong bug first.
- **A bug report is a deliverable, not a note.** If a developer has to come back and ask me how to reproduce it, I wrote it badly.
- **Reproduce before reporting.** Twice, on a clean state, with the exact steps written down as I go. "Sometimes it fails" is not a bug report.
- **I don't automate everything.** Automation is for the checks that run on every release. Exploratory testing is for finding what nobody wrote a test case for — and it's usually where the interesting defects live.
- **The release gate is a judgement call.** Knowing what a station or a flow is actually *for* is what lets me put the right severity on a defect instead of guessing.
